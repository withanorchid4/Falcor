DDGI 光栅捕获：Nsight GPU Trace

已安装 NVIDIA 官方签名的 Nsight Graphics 2026.4，采集 multiview 关闭、开启各 3 帧。RTX 5070 / D3D12 / SponzaLambert / 1080p / 每帧1024 probes / 256方向 / 每面32²。700次Present后采集；锁定base时钟；Top-Level Triage与实时Shader Profiler开启。

结论：瓶颈集中在顶点/几何路径，像素后端和显存带宽不是主因。数据没有证明某一个固定功能几何单元达到吞吐上限。低活跃warp数量及指令依赖等待表明，延迟隐藏与几何工作粒度也应调查。

观察与推断

  • multiview降低PDA输入、顶点属性读取、SM和L2负载，但VPC裁剪输入负载增加，屏幕输出负载基本不变；因此共享输入的收益没有同比转化为帧时间收益。
  • 关闭multiview的Shader Profiler中，vsMain占95.97%的采样，psMain仅0.84%。这是采样比例，不是独占GPU时间。
  • RasterVisibility内warp状态采样中，Wait约38.9%/40.6%，Short Scoreboard约13.3%/9.3%，Long Scoreboard(L1TEX)约12.1%/11.5%。Selected约30.2%/29.2%，它表示成功发射指令，不是stall。
  • Wait是耦合算术数据依赖等待，不能解释成CPU等待或全局barrier；Long Scoreboard也不等价于显存带宽饱和。结合低活跃warp及低显存吞吐，更值得检查VS依赖链、重复probe原点计算、任务粒度及延迟隐藏。
  • 开启multiview时，采样接口把主热点标成Internal Function/fragment；这与专用PS活跃warp和屏幕管线指标不一致，因此不把该内部函数标签作为FS瓶颈证据。

建议的下一轮优化

  1. 先做小范围A/B：预计算每个probe位置/投影参数，避免每个顶点重复解包volume和读取probe数据；必须实测，当前不能保证收益。
  2. 降低提交的几何量：probe捕获LOD、meshlet级保守剔除；此前三角形消融已支持这一方向。
  3. 若继续追根因，采集固定probe集合的multi-pass指标和可关联源码的VS数据，区分资源占用、任务供给和具体依赖链。本轮并未证明某一条源码指令是唯一瓶颈。

不建议继续优先削减FS或cubemap分辨率。完整正确性和长期画质并非本轮测试目标。
