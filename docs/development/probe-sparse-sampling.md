# Probe 稀疏采样与可见性解耦

开工检查点：`169dd96e`。先写本文，再实现与测试。本轮实现保持未提交。

## 依据与范围

Hawar Doghramachi, SIGGRAPH 2020, *Lighting Technology of The Last of Us Part II*，第 3/5/6 节：
https://history.siggraph.org/wp-content/uploads/2022/08/2020-Talks-Doghramachi_Lighting-Technology-of-The-Last-of-Us-Part-II.pdf

原方案在对象 OBB 的八角混合附近 Probe，将 SH 写入 2×2×2 体积缓存，像素三线性读取；对象未移动或变形时复用缓存。其遮挡另行估计，大静态物体还结合顶点亮度补充空间频率。这里借鉴的是“稀疏求值→中间缓存→像素重建”分层，而非复刻完整 Naughty Dog 算法。

本版拟采用屏幕空间稀疏表面采样，适配当前整场景逐像素 Probe 管线。没有跨帧历史，不增加离线缓存版本，不依赖具体可见性方法。每帧重新生成稀疏数据，避免相机运动、切换可见性后残留旧值。先保留默认逐像素，性能/画质验证后决定是否推荐开启。

## 接口与实现契约

- `configureSampling`：`samplingMode=full/screenSparse`、`sparseStride=2/4/8`。与 `configureVisibility` 正交，支持距离矩和实时射线的全部组合，不改 SH、bias 和探针缓存。
- 稀疏求值阶段：每个屏幕采样块的一个真实可见表面点，调用现有完整的 8 Probe 求值器。缓存未乘 albedo 的辐照度、世界位置与法线；背景标无效。分辨率用向上取整，覆盖非整除尺寸。
- 全分辨率着色阶段：读附近四个稀疏点，按屏幕双线性权重重建。材质 albedo、直接光、自发光、背景保持全分辨率。
- 保边条件：法线相似、双向平面距离小于最小 Probe 间距的一定比例、邻点世界距离不过大；不满足则拒绝。没有足够支持或四点辐照度变化大时，调用原求值器回退。不能宣称任意高频阴影完全保留；检查测试结果后收紧或换方案。
- 稀疏构建与精确回退调用同一 `sampleProbeIrradiance`，它内部选择 moments/rayTraced。重建代码不读取距离矩、不发可见性射线、不知道使用哪种后端。
- 点选面板仍显示该点直接求值的八 Probe 数据，必须标注不是重建后的像素权重。另提供稀疏使用/回退输出，避免错误解读。
- 启用 debug 数值视图时保持原精确诊断语义；普通光照 debug 叠加可用稀疏。切换 sampling 不使 baked Ready 失效。
- 不复制相机历史、不减少 GI 之外的着色采样，不默认为高质量=无误差。

## 实施与验收

1. 加参数序列化/UI/Python 接口、稀疏纹理生命周期、构建/重建阶段及独立 GPU profiler 区间。
2. 编译隔离插件，用已保存 Room 高质量缓存与原相机做 `full/sparse2/sparse4/sparse8 × moments/rayTraced` 对照；同时检查第二视角（几何边界）、隔墙和开放场景。
3. 逐像素基准不得发生非预期改变。检查 HDR 有限、开启后回到 full 恢复相同结果、后端切换、相机运动、奇数尺寸及未烘焙状态无旧值污染；检查退化/回退输出。
4. GPU 时间来自 Falcor timestamp profiler，预热排除编译与缓存加载，至少 3 轮、每配置至少 100 帧，轮序交错。记录 Probe pass 总耗时、稀疏构建/全屏着色和整帧 GPU 时间，报告毫秒及百分比，不用帧率标签推断加速。
5. 同后端 full 为画质基准，量化 HDR/显示差异并检查图像，报告精确回退比例与额外显存。射线模式只保证稀疏位置/精确回退位置做真实遮挡，不保证重建位置逐像素射线等价。
6. 若稀疏开销超过收益或漏光/边界损失明显，保留 full 默认，调整重建/分辨率后重测，不把无收益宣称成功。验证后安装插件，保护旧缓存与原始快照。

## 首轮发现与第二轮收紧

首轮全像素基准与上一版 HDR 完全一致，切回 full 也完全一致。4×4 对问题墙面有明显 GPU 收益，但 Room 植物中 46 个射线模式像素的显示差异超过 0.05，开放场景屏幕边缘也有 33 个距离矩模式异常像素。几何平面/法线条件不能区分极近的薄叶片，也不能保证边界处的外推可靠。

因此正式方案新增：缓存点与当前像素须有相同 VBuffer 图元标识（实例/图元/类型的 packed header），否则精确回退；屏幕最外半个采样间隔也精确回退，不做边界外推。优先保留局部几何细节，接受额外回退成本。诊断输出首轮的有效资源宏名称有误，已修正并增加“有效表面计数必须非零”的验收断言，首轮的零回退统计作废。

收紧后开放场景边缘大误差消失，但复杂房间速度变差，部分 alpha 叶片仍有狭窄遮挡变化。因此进一步将 alpha-mask 材质保守地全部精确求值（稀疏构建不为它们做无用的 Probe 查询），任一重建邻居不合格立即回退，避免多余的后续邻居读取。为避免稀疏分支增加 full 的寄存器压力，编译 full/sparse 两种 shader 变体；接口仍是同一采样开关，可见性算法不参与调度定义。每种变体预热后单独计时。

第四轮显示，重建混在含 TraceRay 的 ray-generation shader 中仍会让复杂场景变慢。因此调整执行结构：稀疏 RT 求值 → 独立无射线 Compute 重建 → 全分辨率着色/必要时精确 RT 回退。共享表面读取函数保证法线一致；Compute 只写辐照度和有效标记，不绑定任何距离矩/SH/可见性参数。这增加一张全屏 RGBA32F 中间图和一次表面属性读取，是否划算以新测试为准。

第五轮墙面有收益，但复杂房间精确回退让最终 ray-generation 内出现混合工作量。继续将 Compute 中无法重建的像素用 wave-prefix 压缩到 GPU 队列，独立派发精确求值后再做统一全屏着色。Falcor 当前没有间接 DispatchRays 接口，因此回退派发仍覆盖像素数上限，超过 GPU 计数的线程立即退出；不读回计数，不引入 CPU/GPU 同步。用每 wave 一次原子加减少队列开销。队列最大一条记录/像素，计数每帧清零，背景不入队；有效标记 1 表示重建，2 表示精确回退，统计语义不变。

第六轮队列实验失败：复杂房间 4×4 射线 Probe pass 约 0.484 ms，高于第五轮的 0.449 ms 和逐像素 0.434 ms。队列/额外派发成本超过收益。正式代码已撤掉队列，保留第五轮独立 Compute 重建方案，默认仍 full。队列实验的图像、计时和隔离运行时留在 `build/probe-sparse-validation-06/`，不作为交付配置。

## 最终实测：1280×720，RTX 5080，D3D12

交付代码采用 `build/probe-sparse-validation-05/` 的方案。每配置预热 45 帧，交错顺序测 3 轮，每轮捕获 150 帧，丢弃开头 5 条记录后取中位数，再取三轮中位数。全部缓存已加载，无烘焙、无调试叠加、无图像读回；计时不包含截图。`Probes` GPU 区间包含稀疏构建、Compute 重建和最终全屏着色的总成本，不能仅把稀疏构建时间称为算法成本。

4×4 配置的结果如下（负节省表示更慢）：

| 视角 / 可见性 | 新版逐像素 Probe ms | 稀疏 Probe ms | Probe 节省 | 渲染帧 GPU ms：逐像素→稀疏 |
| --- | ---: | ---: | ---: | ---: |
| 问题墙面 / 距离矩 | 0.1958 | 0.1697 | 0.0261 ms / 13.3% | 0.3784 → 0.3441 |
| 问题墙面 / 射线 | 0.3937 | 0.2476 | 0.1461 ms / 37.1% | 0.5640 → 0.4296 |
| 房间全景 / 距离矩 | 0.2030 | 0.2355 | −0.0325 ms / −16.0% | 0.3871 → 0.4255 |
| 房间全景 / 射线 | 0.4339 | 0.4490 | −0.0151 ms / −3.5% | 0.6185 → 0.6387 |

渲染帧指 profiler 的 `onFrameRender` GPU 区间，不含完整应用 CPU/UI/present 开销，不能用它直接推算窗口 FPS。墙面射线模式该区间减少 23.8%；全景约慢 3.3%。4×4 精确回退占有效表面像素：墙面约 14.18%，房间全景约 37.25%，因此查询总量远不止原来的 1/16。

另测了提交 `169dd96e` 的真实旧插件：墙面距离矩/射线为 0.1946/0.4979 ms，全景为 0.2020/0.4275 ms。旧插件与新 full shader 编译布局并不完全相同，尤其墙面射线已有差异；上表刻意以同一新版本的 full 为基准，不把这部分差异算成稀疏收益。原始结果在 `build/probe-sparse-original-benchmark/`。

2/4/8 间隔的完整记录在 `timing-summary.json`，4×4 汇总及旧插件基线在 `benchmark-report.json`。不能承诺所有场景加速，默认保留 full；平坦大表面可试 4×4，家具/植物较多的场景目前建议 full。
