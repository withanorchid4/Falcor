# WRC 结论记录

本文件集中记录本地 Falcor 的 WRC + DDGI 实验结论。每条保留测试条件、证据和解释边界，后续结论继续追加。测试流程见 [测试方案](测试方案.md)。

## 001｜材质分组 dispatch 在当前场景中明显慢于合批

日期：2026-10-28。对象：本地 WRC 实现的命中代表点着色阶段。

**结论：在 `materials.pyscene` 的当前工作量下，把活动单元按材质类型拆成 11 次 dispatch，明显慢于混合为一次 dispatch。减少材质类型分歧的潜在收益，没有抵消分批执行的总成本。**

### 对比了什么

只切换 `wrcGroupByMaterial`，两种模式都保留 WRC 空间去重：

| 模式 | 活动列表 | 着色执行 |
| --- | --- | --- |
| 开启分组 | 按 `MaterialType` 分为 11 个列表 | 每个列表一次 compute dispatch |
| 关闭分组 | 所有活动单元进入一个混合列表 | 一次 compute dispatch |

两种模式使用同一个 `shadeWRC` / `wrcShadeHit`，完整缓存键、采样数、光照公式和 gather 回退规则相同。这里的一次 dispatch 处理的是去重后的命中代表点。切换会使 WRC 缓存和列表失效，保留 DDGI 探针历史。

### 条件与实测数据

硬件为 RTX 5080，驱动 617.14，D3D12 Release。场景含 11 种材质类型，探针网格 8×6×8，每探针 256 条射线，输出 320×240；哈希表 65,536 槽，`wrcMaxAge=0`、`wrcShadeSamples=1`，计时关闭单元显示。

两个独立进程分别按“开、关、关、开”和“关、开、开、关”测试，每个进程只创建一次场景和渲染图。初始预热 128 帧，每个窗口前再运行 41 帧。窗口采集 192 帧，去掉前 5 条记录后取中位数，再对每种模式的四个窗口中位数取中位数。计时期间持续更新探针，不截图、不读回统计。

| 指标 | 分组开启 | 分组关闭 | 关闭后的变化 |
| --- | ---: | ---: | ---: |
| 着色 dispatch 次数 | 11 | 1 | 减少 10 次 |
| WRC 着色 GPU 耗时 | 0.213952 ms | 0.024576 ms | 降低 88.5%，约 8.71 倍速度 |
| 整个探针更新，含 SDK | 0.317952 ms | 0.127872 ms | 降低 59.8%，约 2.49 倍速度 |
| 几何追踪 | 0.028160 ms | 0.028032 ms | 基本持平 |
| 哈希与列表构建 | 0.004864 ms | 0.004736 ms | 基本持平 |
| gather | 0.005376 ms | 0.005376 ms | 持平 |
| SDK 探针更新 | 0.061824 ms | 0.061696 ms | 基本持平 |

两种模式各采样 16 帧统计，平均有效命中数均为 8,105.1875，平均着色条目数均为 4,121.875，回退数均为 0。合批的加速伴随相同的平均着色工作量。

四个窗口的 WRC 着色中位数范围：分组为 0.2104–0.2171 ms，合批为 0.0225–0.0264 ms。反转测试顺序后结论一致。

### 这说明了什么

分组让同一个 wave 中的任务来自同一种材质类型，有利于减少由材质类型引起的指令分歧。材质参数、纹理和光照计算仍可能产生不同执行路径；本次没有采集 wave 分歧指标，因此尚不能确认实际减少了多少分歧。

当前性能差异有三个可能的解释：

- **批次太小。** 每帧约 4,122 个条目拆成 11 组，平均每组约 375 个。小批次可能不足以充分利用 GPU；各组实际大小也不均匀。
- **重复调度和同步。** 多次 dispatch 增加提交、资源绑定及同步相关成本。这些成本需要与分歧减少带来的收益一起计算。
- **可节省的材质计算有限。** 当前所有组仍执行同一个通用 shader，没有为每种材质生成专用着色程序；DDGI 命中点直接光使用简化的漫反射求值，材质准备仍有类型差异，但不会执行所有材质完整的复杂 BSDF。

**已测得的是分组的净效果明显更差。** 调度、资源同步、GPU 利用率与指令分歧分别贡献了多少，仍需底层 profiling 区分。对于更大的着色工作量、成本更高或使用专用 shader 的材质，应重新测量。

### 使用与验证

在 DDGI 面板取消 **Group shading by material**，或设置 `wrcGroupByMaterial=false`，即可使用混合列表。当前代码默认值仍为 `true`，开关保留用于对照。

两进程正常退出；计数守恒、12 张间接光 HDR 的有限值、切换时保留探针历史、冻结后切换与恢复、两种列表的单元显示、跨帧缓存失效与恢复复用均通过。代表点由并行 CAS 选出，切换顺序也会改变反馈历史，本次未要求逐像素完全一致。

## 002｜关闭材质分组后，默认配置的核心收益来自空间共享着色

日期：2026-10-28。依据：核对当前 WRC 与原 DDGI 的源码调用路径。

**在 `wrcGroupByMaterial=false`、`wrcMaxAge=0`、`wrcShadeSamples=1` 下，WRC 减少计算次数的核心机制，是让多个符合共享条件的命中点只执行一次代表点着色。每条探针射线的几何追踪仍独立执行。**

例如，10 条有效射线命中同一个缓存键，且哈希插入成功：

| 阶段 | 原 DDGI 就地着色 | WRC 合批 |
| --- | --- | --- |
| 探针射线几何追踪 | 10 条射线各自追踪 | 10 条射线各自追踪并记录命中 |
| 命中后的材质与光照求值 | 10 次着色 | 1 次代表点着色，其他命中共享结果 |
| 写入 DDGI ray data | 各自的 radiance 和距离 | 共享 radiance，各自的距离 |
| SDK 探针积分与更新 | 原流程 | 原流程 |

省下的工作包括重复的材质实例准备、直接光采样及其阴影可见性查询、历史 irradiance 查询。WRC 追踪阶段仍需加载表面几何以构造键，代表点着色时还会重新加载表面；缓存命中不会省掉前面的几何追踪和键构造。哈希查找失败等情况在 gather 中逐射线回退着色。

共享条件是完整键一致：LOD、世界单元、材质 ID、量化的有向几何法线和材质类型分组标识。仅仅空间上相邻并不足以共享；关闭分组 dispatch 也不会删除键中的材质信息。不同 probe 发出的射线可以共享同一代表点结果，单元内的纹理、遮挡与光照差异则由代表点近似。

还有一个默认关闭的独立收益来源：设置 `wrcMaxAge>0` 后，超过前 32 次探针更新的预热期，满足完整键、有效年龄和有限值检查的缓存条目可以跨更新复用 radiance，连本次代表点着色也跳过。探针射线仍需追踪，且较旧的 radiance 会延迟光照反馈。

从 ray-generation shader 拆到 compute、紧凑活动列表和 inline shadow query 也会改变执行效率，但目前未单独测得这些变化相对原 DDGI 的净收益。性能必须合计节省的着色成本与新增的命中记录、哈希、列表、同步和 gather 成本。第 001 条的 88.5% / 59.8% 是 WRC 分组与合批之间的差异，不能当作相对原 DDGI 的加速比例。

源码依据：[原 DDGI 的 traceProbes](../../Source/RenderPasses/RTXGIDDGI/RTXGIDDGI.rt.slang)、[WRC 几何追踪](../../Source/RenderPasses/RTXGIDDGI/WorldRadianceCache.rt.slang)、[完整键与代表点着色](../../Source/RenderPasses/RTXGIDDGI/WorldRadianceCache.slang)、[去重、跨帧复用和 gather](../../Source/RenderPasses/RTXGIDDGI/WorldRadianceCache.cs.slang)。

## 003｜合批 WRC 对比原 DDGI：收益随场景变化

日期：2026-10-28。对象：本地 `useWRC=false` 的原 DDGI 就地着色路径，与 `useWRC=true`、`wrcGroupByMaterial=false` 的 WRC 路径。

**相同探针和射线预算下，合批 WRC 在 Cornell 小幅变快，在 Room 变慢，在多材质场景获得较明显收益。关闭材质分组解决了过多批次的成本，但未使 WRC 在所有场景都胜过原路径。**

### 测试条件与方法

RTX 5080，驱动 617.14，D3D12 Release，headless，输出 320×240。三场景均为 8×6×8 探针、每探针 256 条射线，自动包围盒、重定位和分类开启。RTXDI 与 NRD 保持相同配置，探针持续更新，关闭 probe 和 WRC 单元显示。

WRC 使用 `wrcCellScale=0.1`、`wrcLodDistance=8`、`wrcMaxLod=16`、`wrcProbeLimit=16`、`wrcTableSize=65536`、`wrcMaxAge=0`、`wrcShadeSamples=1`。因此只测同次更新内的空间共享，不包含跨帧复用收益。

每个场景按“原 DDGI、WRC、WRC、原 DDGI”启动四个独立进程，共 12 个进程；每个进程只创建一次场景和渲染图，使用相同初始采样种子、相机与探针更新次数。初始预热 256 帧，每个窗口前再预热 40 帧，其中最后 8 帧启用 Profiler，然后连续渲染 256 帧计时。Profiler 实际返回每窗口 255 条时间记录，舍弃前 5 条后取中位数；每种模式的最终数值为六个窗口中位数的中位数。计时期间没有截图或 WRC/探针诊断统计读回，Profiler 自身仍会回收 GPU 时间戳。

### 计时实现与区间边界

使用 Falcor 的 `FALCOR_PROFILE` 和内置 `GpuTimer`。区间开始和结束分别向 GPU 命令流写入 timestamp query，随后取时间戳差，乘以设备提供的毫秒换算系数。报告读取捕获文件中的 `gpu_time` 原始记录，未使用 `cpu_time`、CPU 墙钟或界面的滑动平均值。

`Profiler::Capture` 第一次采集只初始化事件列表，不写入记录，因此 256 次渲染返回 255 条记录；舍弃前 5 条后，每窗口参与统计的是 250 条。每场景、每模式运行两个进程，每进程三个窗口，最后对六个窗口中位数取中位数。

| 区间 | 包含的工作 |
| --- | --- |
| `OriginalTrace` | 原路径射线资源绑定涉及的 GPU 工作、探针几何追踪和就地着色；未单独拆开几何与着色时间 |
| `WRCTrace` | 探针几何追踪、表面几何加载、键构造和命中记录 |
| `WRCBuild` | 哈希槽插入、去重、活动列表构建 |
| `WRCPrepare` | 根据活动列表长度生成间接 dispatch 参数 |
| `WRCShade` | 代表点的材质准备、直接光与阴影查询、历史 irradiance 查询；本次每帧一次 dispatch |
| `WRCGather` | 缓存结果查询、失败命中回退着色、各射线 radiance 与原始距离写回 |
| `SDKUpdate` | irradiance 与距离混合、探针重定位、分类；SDK 内部 kernel 未单独计时 |
| `ProbeUpdate` | 以上对应路径及 SDK 更新，并包含子区间之外的清零、屏障等 GPU 工作 |
| `DDGI/raytraceScene` | 相机可见表面的 DDGI 查询与合成 shader；不包含独立 RTXDI、NRD pass |
| `DDGI` | 整个 render pass，包括探针更新和相机表面处理等工作 |

这是 GPU 命令区间的经过时间，区间内的资源转换、同步和 GPU 等待也可能计入，不能等同于纯 shader 算术时间。`ProbeUpdate` 嵌套在 `DDGI` 内，`WRCShade` 等又嵌套在 `ProbeUpdate` 内，父子区间不能重复相加。

Profiler 在帧末 resolve 时间戳、复制到读回缓冲区，并用 fence 等待上一帧计时完成后读取结果。它会增加测量和同步成本；WRC 的阶段标记也比原路径多，本次未单独扣除插桩开销。因此这些结果是开启 Profiler 时的 GPU 区间对照，不能推导为关闭 Profiler 后的 CPU 帧时间或吞吐率。

源码依据：[阶段标记](../../Source/RenderPasses/RTXGIDDGI/RTXGIDDGI.cpp)、[GpuTimer](../../Source/Falcor/Core/API/GpuTimer.cpp)、[Profiler 的帧末回收与捕获](../../Source/Falcor/Utils/Timing/Profiler.cpp)。

### GPU 耗时

主指标是整个 `ProbeUpdate`，包含射线追踪、命中点着色、WRC 额外流程和 SDK 探针积分更新。变化为 `(WRC / 原 DDGI - 1) × 100%`。

| 场景 | 原 DDGI | 合批 WRC | 耗时变化 | 两模式各六个窗口的范围：原 DDGI / WRC |
| --- | ---: | ---: | ---: | --- |
| Cornell | 0.136704 ms | 0.130944 ms | −4.2% | 0.136704–0.137216 / 0.130048–0.131584 ms |
| Room | 0.163328 ms | 0.172096 ms | +5.4% | 0.162944–0.163840 / 0.171264–0.173696 ms |
| Materials，11 种材质类型 | 0.156160 ms | 0.128128 ms | −18.0% | 0.154624–0.157312 / 0.127744–0.128512 ms |

包括相机可见表面计算的整个 DDGI pass，耗时分别为：

| 场景 | 原 DDGI | 合批 WRC | 耗时变化 |
| --- | ---: | ---: | ---: |
| Cornell | 0.168832 ms | 0.163968 ms | −2.9% |
| Room | 0.203776 ms | 0.215808 ms | +5.9% |
| Materials | 0.181760 ms | 0.154560 ms | −15.0% |

### 为什么着色次数与最终收益不成比例

以下为每种 WRC 配置的 24 次统计采样均值；每次更新只有一次 WRC 着色 dispatch。有效命中数取自 WRC 追踪阶段，作为没有共享时逐命中点着色调用数的参照。

| 场景 | 有效命中 | 代表点着色 | 回退着色 | 总着色调用减少 |
| --- | ---: | ---: | ---: | ---: |
| Cornell | 54,007.83 | 6,623.17 | 0 | 87.7% |
| Room | 52,499.58 | 24,646.25 | 2.08 | 53.1% |
| Materials | 8,127.58 | 4,128.00 | 0 | 49.2% |

Cornell 合并了最多的着色调用，但整个探针更新只快约 4.2%；Materials 合并比例较低，最终收益反而更大。减少调用次数只是一个因素，每次着色的成本、剩余几何追踪、SDK 更新与缓存管理成本共同决定总时间。

| GPU 阶段（ms） | Cornell | Room | Materials |
| --- | ---: | ---: | ---: |
| 原 DDGI：追踪与就地着色合计 | 0.069248 | 0.093056 | 0.095744 |
| WRC：几何追踪与命中记录 | 0.029312 | 0.038528 | 0.028160 |
| WRC：哈希与列表构建 | 0.007168 | 0.010688 | 0.004352 |
| WRC：生成调度参数 | 0.001536 | 0.002048 | 0.001536 |
| WRC：代表点着色 | 0.015552 | 0.033344 | 0.025856 |
| WRC：gather，含回退 | 0.008704 | 0.016896 | 0.005376 |
| SDK 更新：原 DDGI → WRC | 0.067072 → 0.066560 | 0.070016 → 0.069504 | 0.060032 → 0.060672 |

原路径的追踪与着色记录在同一个计时区间，应与 WRC 的整套对应阶段比较。Room 的哈希、调度参数准备和 gather 合计约 0.0296 ms，加上追踪与代表点着色后已超过原路径的约 0.0931 ms。各阶段分别取中位数，且阶段之间还有同步等工作，表中分项之和不要求与总时间完全相等。

### 图像差异和验证范围

这是一组相同采样预算下的性能比较。WRC 共享代表点会改变空间近似和采样相关性，不能据此声称等画质加速。按相同探针更新次数比较六对单帧线性间接光 HDR：

| 场景 | WRC / 原 DDGI 的 RGB 均值比 | 平均单帧相对 RMSE |
| --- | ---: | ---: |
| Cornell | 0.9965 | 0.65% |
| Room | 0.8837 | 26.66% |
| Materials | 0.9811 | 7.07% |

Room 的间接光均值约低 11.6%，需要在评价该配置时同时考虑。相对 RMSE 为 `sqrt(sum((WRC - 原 DDGI)^2) / sum(原 DDGI^2))`，先逐帧求值，再对六对图取均值。这些差异包含随机采样和历史反馈差异；原 DDGI 是对照路径，本轮没有检验 PathTracer 真值或长期收敛。

12 个进程均正常退出；36 张间接光 HDR 为有限值，输出非黑且无显著负值。WRC 的射线与条目计数守恒、两路径对应采样帧的探针更新次数、活动探针数、重定位数量和体积边界一致。验证通过表示上述运行与一致性检查通过，图像差异另行报告。

## 004｜Room 缩小空间单元：差异显著收敛，复用收益随之下降

日期：2026-10-28。问题：第 003 条中 Room 的间接光差异较大，缩小共享范围是否能改善结果？

**将 `wrcCellScale` 从 0.1 降到 0.01 后，相对原 DDGI 的单帧 RMSE 从约 27.25% 降到 1.39%，间接光 RGB 均值从低约 10.98% 改善到低约 0.53%。同时着色调用减少比例从 53.05% 降到 1.62%，探针更新耗时比原 DDGI 高约 22.4%。**

### 改动与控制变量

本轮缩小的是世界空间单元宽度，哈希表容量始终保持 65,536 槽。`Cell scale` 乘以最小探针间距得到基础单元宽度；Room 本轮实际最大 LOD 为 1，所有有效命中均未使用粗 LOD。因此第 003 条的差异并非由远距离 LOD 放大单元造成。

| Cell scale | 相对原单元宽度 | 实际单元宽度（世界单位） |
| --- | ---: | ---: |
| 0.1 | 1 | 0.063408 |

## 005：放大材质分歧后，分批 dispatch 在什么条件下获益？

日期：2026-10-28。场景为 `materials.pyscene`，包含 11 种材质类型。

**本次实验中，约 97,000 个着色条目、每种材质增加 10,000 轮独立循环时，分批使 WRCShade 从 2.776448 ms 降至 1.513088 ms，减少 45.50%；整个 probe 更新从 3.544832 ms 降至 2.302464 ms，减少 35.05%。** 原规模约 4,100 个条目时，即使增加同样的循环，分批仍较慢。未加合成负载时，四种配置均是混合 dispatch 更快。

### 两种调度策略的实验流程

两个模式都启用 WRC（`useWRC=true`）：先记录射线命中，再通过哈希合并选出每个占用单元的代表点，最后比较这些代表点的两种着色调度方式。

```text
WRCTrace：追踪 probe 射线，记录命中信息
    ↓
WRCBuild：按相同的完整键进行哈希合并，每个占用单元选一个代表点
    ↓
组织本帧的活动缓存条目列表
    ├─ 混合：所有活动条目进入一个列表
    │         wrcGroupByMaterial=false
    └─ 分批：按 MaterialType bucket 进入 11 个列表
              wrcGroupByMaterial=true
    ↓
WRCPrepare：根据各列表长度生成间接调度参数
    ↓
WRCShade：一次混合 dispatch / 11 次按类型 dispatch
          对代表点着色，将 radiance 写入对应缓存单元
    ↓
WRCGather：各条射线取回所属单元的 radiance，写入 probe ray data
    ↓
SDKUpdate：更新探针 irradiance、距离及探针状态
```

活动列表在 `WRCBuild` 插入新单元时构建。这里的“所有缓存”指本帧需要着色的活动条目；空槽不参与着色。本实验设置 `wrcMaxAge=0`，每个活动单元本帧都重新计算 radiance。射线命中记录与已着色的 radiance 缓存是两个阶段，记录命中时尚未完成代表点着色。

所谓“分 shader”实际按材质类型组织条目，11 次 dispatch 调用同一个 `shadeWRC` compute shader。两个模式使用相同的射线配置、哈希键、合并规则、实际着色算法，以及配对的合成负载模式和循环次数；主要变量是列表组织与 dispatch 方式。两种模式分别执行完整更新流程，代表点选择和列表顺序可以随 GPU 调度变化。

缩小单元后，更多命中会成为独立的活动条目，所以混合模式即使仍然只有一次 dispatch，也要执行更多线程和着色工作。最后的细单元配置同时将 `cell scale` 从 0.1 改为 0.01、最大 LOD 倍率从 16 改为 1；探针数量与每 probe 射线数保持上一组的设置。

### 实际材质分歧的位置

函数名是 `setupMaterialInstance()`。当前调用关系为：

```text
shadeWRC → wrcShadeHit
  → gScene.materials.getMaterialInstance(sd, ExplicitLodTextureSampler(0))
    → getMaterial(sd.materialID)
      → getMaterialType → createDynamicObject<IMaterial>(type, data)
    → material.setupMaterialInstance(...)   // 各材质类型的接口实现
  → material.getProperties(sd)              // IMaterialInstance 接口
  → evaluateDirect(..., diffuseOnly=true) + DDGI irradiance 反馈
```

证据见 [MaterialFactory.slang](../../Source/Falcor/Scene/Material/MaterialFactory.slang) 的 `getMaterial()`、`getMaterialInstance()` 和 [IMaterial.slang](../../Source/Falcor/Rendering/Materials/IMaterial.slang) 的接口声明。普通 DDGI 和 WRC 都通过这套材质工厂初始化命中点材质。探针直接光采用简化的 diffuse 求值，但材质初始化仍可能按类型和参数走不同代码。

这是 Slang 的动态接口分派。当前分组让一批条目的材质类型相同；11 批仍使用同一个 compute shader，并未针对每种材质单独编译专用版本，也不能消除同类型材质内部的所有参数分支。

### 合成负载与对照

实验限定在 WRC 的材质初始化附近，真实 Standard、Hair、Cloth 等材质实现保持原样。新增 [WorldRadianceCacheStress.slang](../../Source/RenderPasses/RTXGIDDGI/WorldRadianceCacheStress.slang)，按现有材质类型 bucket 选择 11 条不同循环，模拟昂贵的材质类型分支。

| 属性 | 含义 |
| --- | --- |
| `wrcStressMode=0` | 关闭合成负载，编译时移除其调用；默认值 |
| `wrcStressMode=1` | 所有类型执行同一个循环，作为共同代码对照 |
| `wrcStressMode=2` | 11 个 bucket 各自执行不同顺序的循环 |
| `wrcStressIterations` | 运行时循环次数，默认 0，上限 10,000 |
| `wrcStressStats` | wave 类型数与校验值诊断；正式计时关闭 |

每轮包含两次移位、两次 XOR、一次整数乘法和一次加法，后一步依赖前一步结果。各类型改变这些运算的顺序、移位数和常数。这是每轮相同数量的源码级运算，不保证 GPU 机器指令数完全相同。输入来自实际命中位置与 ray ID，结果写入 WRC radiance 未用于光照的 alpha 通道，防止无效代码删除；RGB、随机采样流和 irradiance 计算未添加合成贡献。

独立包装实际 stress helper，以 Slang/DXC `-O3`、`cs_6_5` 编译后，DXIL 保留了类型 switch、11 个循环回边和校验值 UAV 写出。此检查针对该 helper，不是完整 WRC shader 的 GPU ISA 分析。[编译检查记录](../../build/wrc-stress-inspect/compiler-check.json)；[DXIL](../../build/wrc-stress-inspect/inspect.dxil.txt)。运行时也验证了非零校验值、受压条目数与实际着色条目数相等，以及关闭实验后校验与受压计数归零。

### 条目规模与计时方法

RTX 5080，驱动 617.14，D3D12 Release，输出 320×240；RTXDI、NRD、探针重定位与分类保持开启。WRC 跨帧复用关闭，每条目一次实际光照采样。四组统一使用 262,144 个 hash 槽、64 步探测预算，以避免回退着色混入 gather。所有统计快照中回退数均为 0。

| 配置 | Probe 数量 × rays/probe | 总射线预算 | Cell scale / 最大 LOD 倍率 | 平均着色条目，约 |
| --- | --- | ---: | --- | ---: |
| 原规模 | 8×6×8 × 256 | 98,304 | 0.1 / 16 | 4,100 |
| 探针 8 倍 | 16×12×16 × 256 | 786,432 | 0.1 / 16 | 13,200 |
| 射线预算 16 倍 | 16×12×16 × 512 | 1,572,864 | 0.1 / 16 | 18,300 |
| 细单元 | 16×12×16 × 512 | 1,572,864 | 0.01 / 1 | 97,000 |

前三组说明，增加射线预算不等于同比增加着色条目，WRC 会合并命中。第四组缩小单元并关闭 LOD 放大，减少合并。它也改变了代表点分布与列表局部性，因此跨配置的差异不能全部归因于条目数量；每行的分批/混合比较使用相同配置。

每种配置运行两个独立进程，使用 ABBA/BAAB 顺序，并反转负载扫描顺序。初始预热 128 帧，每窗口切换后预热 64 帧，再启用 profiler 预热 8 帧，随后渲染 96 帧。Falcor capture 返回 95 条 timestamp 记录，丢弃前 5 条，取剩余 90 条的中位数；下表取每模式四个窗口中位数的中位数。共 8 个正式进程、192 个计时窗口。

计时仍使用第 003 条说明的 Falcor GPU timestamp；`WRCShade` 包含全部 1 次或 11 次着色 dispatch。wave 诊断、统计读回和截图在计时窗口之外，每窗口取四个统计快照。材料类型均为 11，分组后每个有效 wave 只有一种类型；混合模式平均约为 6.5、7.0、7.3、4.4 种。列表顺序及代表点存在调度差异，两个模式的条目数接近但不强制完全相同。

### 结论与适用范围

分批的代价包括额外调度、列表维护以及小批次并行度不足；收益来自同一 wave 不再执行多种材质类型的长分支。本次约 4,100 条目拆成 11 批后，即使每个条目很重，仍然比混合慢；约 97,000 条目配合足够重的类型分支时，收益才超过这些成本。小批次资源利用率的解释来自时序与共同循环对照，本次没有采集硬件 occupancy 或 stall 计数器。

这验证了当前分组方式存在获益条件，也保留了第 001 条的结论：**现有材料的实际 DDGI 着色仍较轻，当前四种规模下关闭合成负载后，分批都更慢。** 此负载模拟类型相关的依赖 ALU 运算，未模拟纹理访问、寄存器压力增长或真实复杂 BSDF；不能把 1.84 倍的合成着色加速当作当前真实材质的加速。

Release 构建成功；8 个正式进程正常退出，8 张最终间接光 HDR 通过有限值、非黑、非负检查。全部快照通过条目/射线守恒、零回退、零跨帧复用、零非有限结果检查。两批运行保存的源码和二进制摘要与最终实验源码相符。默认合成负载关闭，所有 worker 结束前也验证了关闭后的路径；未改全局探针默认值或自动启用材质分组策略。
